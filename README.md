# retrieval-arena

在 BEIR 公开基准上对照四条检索基线，量化**混合检索（hybrid）相对单路的精度增益**，以及**近似最近邻（ANN）在「召回—延迟」上的取舍**。

一句话结论：在 BEIR SciFact 上，BM25 与稠密向量经 RRF 融合后 nDCG@10 = **0.6853**，比单路最好成绩高 **2.09 个点**；NFCorpus 上同样高 **2.85 个点**。代价几乎为零——融合线的延迟由 BM25 主导，稠密只贡献 0.2 ms。但**单数据集上的参数最优结论大多不可复现**，见「跨数据集复现性」。

---

## 这个仓库回答什么问题

工业检索系统几乎都在用「稀疏 + 稠密 + 融合 + 重排」这套组合，但**各自的边际贡献有多少**、**每提升一个点的精度要付多少延迟**，不同任务差别很大。本仓库用一个公开、可复现的框架把这两条曲线测出来。

四条对照线：

| 线 | 实现 | 回答的问题 |
|---|---|---|
| **B1 稀疏** | BM25（自实现倒排索引） | 关键词匹配的天花板在哪 |
| **B2 稠密** | all-MiniLM-L6-v2 + Faiss HNSW | 语义召回比关键词强多少 |
| **B3 混合** | RRF 融合 B1 + B2 | 融合能拿回多少，是否值得多这一层 |
| **B4 混合+重排** | cross-encoder 重排 top-100 | 精度的上限，以及它的延迟代价 |

外加一条 **IVF-PQ**，看量化把召回压掉多少。

## 快速开始

```bash
python -m venv .venv
.venv\Scripts\activate            # Windows；Linux/macOS 用 source .venv/bin/activate
pip install -r requirements.txt

# 国内网络：从 ModelScope 拉模型到本地（HF 直连不通，hf-mirror 在部分网络下也会被中断）
python scripts/download_model.py

# 一条线跑通（自动下载数据 + 建索引 + 评测 + 存结果）
python scripts/run_bm25.py --dataset scifact     # B1
python scripts/run_dense.py  --dataset scifact --sweep-ef   # B2 + 扫参
python scripts/run_hybrid.py --dataset scifact   # B1/B2/B3 对照
```

数据集（约 5 MB）首次运行时自动下载；文档向量会缓存到 `data/_emb_cache/`，重跑不用重新编码。

## 结果

### 主表 · SciFact（5,183 文档 / 300 条已标注 query）

`top_k=100`，稠密用 all-MiniLM-L6-v2（384 维）+ HNSW（M=32, efSearch=64），融合用 RRF k=60，gain 口径 `trec`。

| 线 | nDCG@10 | Recall@100 | MRR@10 | P50 | P99 |
|---|---|---|---|---|---|
| **B1** BM25 | 0.6645 | 0.8892 | 0.6325 | 8.46 ms | 18.37 ms |
| **B2** 稠密 HNSW | 0.6451 | 0.9250 | 0.6047 | 0.21 ms | 0.80 ms |
| **B3** RRF 融合 | **0.6853** | **0.9543** | **0.6475** | 9.34 ms | 20.88 ms |

**融合比单路最好成绩高 +2.09 个点（nDCG@10），召回多拿回 +2.93 个点（R@100）。**

三条值得说的观察：

1. **BM25 在 nDCG@10 上打败了稠密**（0.6645 vs 0.6451）。SciFact 是科学论断检索，query 里大量专有名词和术语，关键词精确匹配的收益高于语义泛化——「稠密一定更强」是错觉，要看任务。
2. **但稠密的 R@100 高 3.6 个点**。说明稠密并不是"找得准"，而是"召回池更全"：它把候选找齐了，只是头部排序不如 BM25。这正是融合有效的机制——融合吃的是两边的并集。
3. **融合的延迟几乎等于 BM25 的延迟**（+0.9 ms）。因为稠密只占 0.2 ms，瓶颈全在 BM25 的 Python 倒排上。工程含义：加融合这一层几乎不额外花钱。

### 第二数据集 · NFCorpus（3,633 文档 / 323 条已标注 query）

同样的参数设置，只换数据集：

| 线 | nDCG@10 | Recall@100 | MRR@10 | P50 | P99 |
|---|---|---|---|---|---|
| **B1** BM25 | 0.3117 | 0.2364 | 0.5205 | 0.36 ms | 7.42 ms |
| **B2** 稠密 HNSW | 0.3158 | 0.3112 | 0.5060 | 0.19 ms | 0.69 ms |
| **B3** RRF 融合 | **0.3443** | **0.3268** | **0.5479** | 0.85 ms | 7.81 ms |

融合再次高 **+2.85 个点**。**融合增益在两个数据集上复现了**——这是本仓库最硬的一条结论。

### 参数敏感性：efSearch 扫参（召回—延迟曲线数据）

`top_k` 固定为 10（**必须** ≤ 最小 ef，否则 faiss 会把 ef 抬到 top_k，曲线被拉平——这个坑我踩过一次）。

| efSearch | Recall@10 | nDCG@10 | P50 | P99 |
|---|---|---|---|---|
| 16 | 0.7683 | 0.6348 | 0.089 ms | 1.107 ms |
| 32 | 0.7733 | 0.6363 | 0.084 ms | 0.327 ms |
| **64** | **0.7833** | **0.6451** | 0.153 ms | 0.441 ms |
| 128 | 0.7833 | 0.6451 | 0.218 ms | 0.714 ms |
| 256 | 0.7833 | 0.6451 | 0.498 ms | 1.628 ms |

**拐点在 ef=64**：从 64 涨到 256，P50 慢了 3.3 倍，精度一点没涨。5k 文档规模下 HNSW 早就饱和了——这个结论只在小规模成立，文档量上去后拐点必然右移。

### 两个反直觉的发现

**发现一：RRF 的 k=60 在本任务上不是最优。**

| RRF k | nDCG@10 | Recall@100 |
|---|---|---|
| 10 | **0.7034** | 0.9543 |
| 60（文献默认） | 0.6853 | 0.9543 |
| 100 | 0.6843 | 0.9543 |

k=10 比 k=60 高 **1.81 个点**，而召回完全一样。含义：本任务里两条线的头部排名一致性较高，把权重更集中在头部（k 小）收益更大。**「k=60 是默认值」不等于「k=60 对本任务最优」**——不扫一遍不会知道。

**发现二：min-max 归一化加权融合在 SciFact 上打败 RRF——但在 NFCorpus 上反过来。**

| 融合方式 | SciFact nDCG@10 | NFCorpus nDCG@10 |
|---|---|---|
| RRF (k=60) | 0.6853 | **0.3443** |
| 归一化加权 (0.5 / 0.5) | **0.7116** | 0.3369 |

SciFact 上加权高 2.63 个点，NFCorpus 上低 0.74 个点。**这个结论不稳健。**

诚实的解释：RRF 丢弃分数大小、只留名次；当两条线的分数分布本身可比且携带置信度信息时，归一化加权能吃下这部分信息。但 min-max 归一的尺度依赖当次查询的分数极值，换个数据集就可能失配——正是 RRF 当初被设计出来要避免的问题。**单数据集上跑出个反例，不等于推翻了 RRF**，只说明"在本任务、本参数下，加权更优"。

### 跨数据集复现性（这一节是重点）

| 结论 | SciFact | NFCorpus | 是否稳健 |
|---|---|---|---|
| 融合 > 单路最好成绩 | +2.09 点 | +2.85 点 | **稳健** |
| 融合后 R@100 同步提升 | +2.93 点 | +1.56 点 | **稳健** |
| 稠密 vs BM25 谁更强 | BM25 胜（nDCG） | 稠密胜（nDCG） | **不稳健**，取决于任务 |
| RRF k=60 是否最优 | 否（k=10 高 1.81 点） | 是（三点差 0.05 点内） | **不稳健** |
| 加权 vs RRF 谁更好 | 加权胜 | RRF 胜 | **不稳健** |

**唯一在两个数据集上都成立的，是"融合带来稳定增益"。** 其余四条都是单数据集上会骗人的结论——这恰好是本仓库最有价值的一条方法论：**一次实验能证明的东西，比它看起来少得多。**

> **评测框架正确性校验**：BEIR 官方公布 BM25 在 SciFact 上 nDCG@10 = 0.665、NFCorpus 上 = 0.325。本实现得 0.6645（差 0.0005）与 0.3117（差 0.013）。
> 差异来源：官方用 Anserini 的 Porter 词干化 + 停用词表，本实现是最朴素的 `lower() + 正则切分`。**先对齐基线，才有资格谈改进。**

## 评测口径说明

三处容易搞错、直接影响数字可比性的地方：

1. **相关性判定用 `rel > 0`**，不是 `doc_id in qrels`。BEIR 的 qrels 里显式写了 `score=0` 表示「判定为不相关」，当成命中会虚高。
2. **gain 有两种口径**：`raw`（gain = rel，BEIR leaderboard 用）与 `trec`（gain = 2^rel − 1，TREC 标准）。0/1 标注下等价；SciFact 是 0/1，NFCorpus 是 0/1/2。跑结果时标明用哪个。
3. **延迟只对有标注的 query 计时**，且先预热 20 次。无标注 query 检索结果为空，会拉低平均延迟；不预热则 P99 被冷启动污染。

## 已知边界

- 离线全量重建索引，**没有增量更新**（在线服务必须支持）。
- 语料规模 5k 级，与工业级千万级文档的长尾分布差异大。
- 不支持结构化过滤 + 向量的混合查询（Filter-First / ANNS-First），这是下一步方向。
